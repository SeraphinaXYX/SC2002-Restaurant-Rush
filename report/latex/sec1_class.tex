\section{UML Class Diagram}
\label{sec:class}

Figure~\ref{fig:class-full} is the class diagram of our final design. It was checked line by line
against the \texttt{stage-3} source, so every class, field and operation in it exists in the code
under the same name and with the same parameters. To keep it readable we left out plain getters
(such as \texttt{getId()} or \texttt{getStatus()}) and constructors that only copy their
arguments into fields. A constructor is shown when it carries a design decision, for example
\texttt{Menu(includeCombos)} or \texttt{Restaurant(tableCount)}.

\paragraph{Notation.} We use standard UML~2 notation:
\texttt{+}~public, \texttt{-}~private, \texttt{\#}~protected;
\emph{italic} operations are abstract and \underline{underlined} members are static.
Operations with no return type return \texttt{void}.
A solid line with a hollow triangle is generalisation and a dashed one is interface realisation.
A filled diamond is composition, a hollow diamond is aggregation, a solid line (with an open
arrowhead when it is navigable in one direction only) is an association, and a dashed line with
an open arrowhead is a dependency. The shaded panels group the classes into the boundary, control,
staff and entity layers. A few associations and dependencies are not drawn because they would
only add crossing lines, for example \texttt{GameController}~$\rightarrow$~\texttt{Menu}; they are
all listed in Table~\ref{tab:relationships}.

\subsection{Encapsulation, Polymorphism and Composition}
\begin{sloppypar}

\paragraph{Encapsulation.} All instance fields are private; the only public fields are
\texttt{static final} constants (the base setting in \texttt{GameConfig} and
\texttt{HappyHour.RECOVERY}). State changes go through methods that check the current state first. \texttt{Order.advancePrep()} only accepts an order that is
\texttt{PLACED} or \texttt{COOKING} and turns it \texttt{READY} after its last unit.
\texttt{Restaurant.seatAt()} refuses a customer who is not \texttt{WAITING} and a table that is
already occupied, and returns the reason in an \texttt{ActionResult}. \texttt{Order.priceCents}
is final and has no setter, which is how we meet the rule that a price is locked when the order
is taken. \texttt{WaitingQueue.getAll()} and \texttt{Restaurant.getOrders()} return read-only
lists, so \texttt{GameView} can print the state but cannot change it.

\paragraph{Polymorphism.} The three customer types differ only through overridden methods:
\texttt{getSatisfactionLoss()} (8, 5, 12), \texttt{applyDiscount()} (the VIP takes 10\% off),
\texttt{chooseItem()} (the Critic always picks the most expensive single dish, never a combo)
and \texttt{onServed()} (the Critic gains 5 if served within two turns of ordering and loses 10
otherwise). \texttt{GameController} and \texttt{Waiter} only ever hold a \texttt{Customer}
reference, and \texttt{Waiter.serve()} calls \texttt{receiveDish()}, which calls the overridden
\texttt{onServed()}. The same idea applies to \texttt{OrderItem}: \texttt{Chef.prepare()} works on
a \texttt{ComboMeal} exactly as on a \texttt{MenuItem}, because \texttt{Order.advancePrep()} only
calls \texttt{getPrepUnits()}.

\paragraph{Composition and aggregation.} \texttt{Restaurant} owns its tables and its waiting
queue, and \texttt{GameController} owns the \texttt{Restaurant}, the \texttt{Menu}, the staff and
the optional \texttt{Host} and \texttt{HappyHour}; none of these outlive their owner. We used
aggregation where the parts are shared. Customers are referenced from the restaurant, the queue
and a table at the same time, and a \texttt{ComboMeal} points to two \texttt{MenuItem} constants
that every other order also uses.
\end{sloppypar}
